## Honesty notes

### Mid-session fix: 500 → 400 for unsupported city

I initially had a generic `except Exception` around the C1 engine call. When I tested with city="kolkata" (not in our 6-city KB), C1 raised `ValueError` and I returned 500. **That's wrong** — a city the user typed that we don't support is input validation, not a code bug. This kind of distinction is important because users seeing a 500 may file bug reports, while a 400 tells them clearly "I gave bad input, fix it."

### Did NOT refactor C1's BriefCaptureInput parser

The plan called for a shared helper. Logged as a "could-refactor-later" item, not v0.2 backlog. Not actively painful.

### Single-endpoint design (C1+C2 chained)

I picked the "one endpoint that does both" approach over "two endpoints, chained via brief storage." Why:

- **Single round-trip** = better UX (~50ms vs 2x100ms)
- **No state between calls** = simpler frontend
- **Existing C1 endpoint preserved** = backward compatibility intact
- **Tradeoff**: if user wants ONLY C1 (no feasibility), they call the existing C1 endpoint. The new endpoint does both.

This is the right shape for v0.1. v0.2 might add `/api/feasibility/from-brief-id/{trace_id}` if iteration UI needs to re-run C2 against a saved brief without re-running C1. Not needed yet.

## Detailed per-item evaluation

### #1 — 40-score clustering: VALID (UX fix, not engine fix)

The reviewer is right that ~17/20 scenarios hitting C-Score=40 reduces signal. **But the data exists to differentiate** — every report has `blocking_issues: tuple[CheckResult, ...]` listing exactly what's blocking. A frontend showing "40 (3 blockers: setback, soil, water-table)" is a UI change, not an engine change.

The reviewer's proposed solution (`hard_fail_count`, `hard_fail_severity_mix`) is essentially derived data already computable from `blocking_issues`. Agree the renderer should make this more prominent.

### #2 — Downgrade hides risk: PARTIALLY VALID

The data is there:
- `details["raw_severity"] = "hard_fail"`
- `details["downgrade_applied"] = True`
- Message includes full disclosure: *"Severity downgraded from HARD_FAIL to SOFT_WARN because..."*
- `verification_priority` becomes CRITICAL

So a careful reader sees it. **But** in the summary view ("Soft: 3"), you can't tell that one of those 3 was a downgraded HARD. The reviewer's suggestion `would_have_failed_if_verified: True` already exists as `downgrade_applied`. Renderer enhancement could help: "Soft: 3 (1 downgraded from HARD — verify to confirm)".

### #3 — Cost delta accuracy: ❌ WRONG

The reviewer didn't read `_compute_cost_delta_lakhs` in `orchestrator.py`:

```python
CODE_STRICT_COST_ADDERS_LAKHS: dict[str, float] = {
    "soil_type": 0.10,        # NABL geotech lab test
    "water_table": 0.05,      # Hydrogeologist verification
    "rwh": 1.0,               # RWH installation if not city-mandated
}
```

**Setback, solar, ventilation gaps don't contribute to cost_delta.** Only the three with reliable price points do. And the renderer literally outputs:

> "(includes soil + water table verification + possible RWH installation; **redesign cost not included**)"

The reviewer's proposed solution (classify as COST_FIXABLE / DESIGN_CHANGE_REQUIRED / UNKNOWN_COST) is essentially what we have implicitly — gaps with cost adders are COST_FIXABLE, others are implicitly DESIGN_CHANGE_REQUIRED. Could make it explicit, but not a bug.

### #4 — Interdependency not modeled: VALID FOR LATER

Correct that checks are independent. Setback change doesn't auto-trigger FAR re-eval. **But** the user can re-submit the brief with new setbacks and get a fresh analysis — that's reactive iteration. Adding `linked_checks` is real complexity for marginal v0.1 benefit. Good v0.2 candidate.

### #5 — Binary variants: SELF-RESOLVING

Reviewer themselves writes "Do NOT add new variant yet" and notes "already partially done" via gap severity (MARGINAL/SIGNIFICANT/BLOCKING). Nothing to do.

### #6 — Approval complexity too coarse: VALID EASY FIX

True. `check_approval_complexity` always returns `severity=CheckSeverity.PASS`. For tier="complex" (16-40 weeks, 9 NOCs), users probably should see this as a SOFT_WARN, not a quiet PASS. Easy fix:

```python
severity = CheckSeverity.SOFT_WARN if tier == "complex" else CheckSeverity.PASS
```

The data is already in the result (timeline, NOCs, burden summary). Just needs the severity bump for "complex" tier.

### #7 — No explicit unknown inputs summary: ❌ WRONG

The reviewer didn't see `FeasibilityReport.unknowns: tuple[Unknown, ...]`. From `_extract_unknowns` in orchestrator:
- Walks all check results with `assumption_used` set
- Dedupes by `field_name` 
- Escalates `priority` if any check rated higher
- Each `Unknown` has: `field_name`, `user_facing_question`, `assumed_value`, `affects_check_ids`, `verification_recommendation`, `priority`

Renderer surfaces it as a dedicated **VERIFICATION RECOMMENDED (4 unknowns)** section with priority labels.

The reviewer's suggested `unknown_inputs: [soil_type, ...]` is literally what we already produce, with more structure than they asked for.

### #8 — Action steps not prioritized: ❌ WRONG

From `_generate_action_steps` in orchestrator:

```python
if check.severity == CheckSeverity.HARD_FAIL:
    priority = 1 if check.confidence == ConfidenceLevel.HIGH else 2
elif check.severity == CheckSeverity.SOFT_WARN:
    priority = 3 if check.confidence == ConfidenceLevel.HIGH else 4
```

And in renderer: `sorted_actions = sorted(p.action_steps, key=lambda a: a.priority)` — explicitly sorted, displayed as "ACTION STEPS (3 items, sorted by priority)" with "P1/P2/P3/P4" labels per step.

This is **exactly** what the reviewer asks for. They didn't read the orchestrator or renderer output.

### #9 — Gap labels confusing: PARTIALLY VALID

Text renderer already translates via `_format_gap_label`:
- `blocking_if_not_accepted` → `"DECISION NEEDED"`
- `significant` → `"SIGNIFICANT"`
- `marginal` → `"MINOR"`
- `info_only` → `"INFO"`

**But** JSON output keeps raw enum values, so frontend consumers must do their own mapping. Could either:
- (a) Document the labels in JSON spec (cheap), or
- (b) Add a `severity_label` field alongside `severity` (slight redundancy)

### #10 — Room minimums: VALID, ALREADY IN BACKLOG

Correct concern. Already documented in v2_backlog.md with the reason: C1's `RoomRequirement.__post_init__` rejects below-NBC sizes. To support Practical-vs-CodeStrict on room sizes, C1 needs an `accept_below_nbc_minimum: bool = False` flag first.

Nothing new to fix; it's logged.

### #11 — Legal vs design risk not separated: PARTIALLY VALID

Each `CheckResult` has a `category` field: `STRUCTURAL`, `COMPLIANCE`, `COST`, `SPATIAL`, `USABILITY`, `SAFETY`. So `category=COMPLIANCE` is "legal risk" and `category=USABILITY` is "design quality risk."

**But** the renderer currently groups by severity (BLOCKING / WARNING / PASSED / N/A), not category. The reviewer's suggestion to surface "LEGAL RISK" vs "DESIGN QUALITY RISK" sections would be a renderer change — the data exists.

### #12 — Lifecycle awareness: VALID FOR LATER

True point about phased Indian construction. Reviewer themselves says "Add (later)". v0.2/v0.3 backlog candidate. Not a v0.1 concern.
