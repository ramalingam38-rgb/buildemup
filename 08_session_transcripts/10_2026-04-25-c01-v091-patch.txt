### Design decisions made during build

**Zero-framework stack.** I went with stdlib `http.server` instead of Flask/FastAPI because (a) Component 7 has no framework dependency and adding one now is scope creep, (b) Railway needs no extra buildpack — just Python 3.10+ and a `PORT` env var, (c) Flask/FastAPI can swap in later with zero engine changes since all HTTP handling is isolated to `api/server.py`.

**Vanilla JS over React/Vue.** Per SPEC Section 9.2: no build step, deploys as-is, works offline once HTML is loaded. The form is about 520 lines of readable JS — React would have added ~200KB of dependencies for functionality we genuinely don't need at v0.1 scale.

**localStorage-only save/resume.** Per SPEC Section 8: email-resume-link needs server-side state, so v0.1 uses browser localStorage with a 12-char hex token. The `tryResume()` function reads `?resume=TOKEN` from URL query string on page load. User gets clear "this browser only" disclosure inline and in the saved-later alert.

**Vastu items loaded from API (not hardcoded in frontend).** Single source of truth — `VASTU_PARTIAL_ITEMS` lives in `domain/brief.py` and propagates to the frontend via `GET /api/vastu/partial-items`. If the 7 items ever change, backend and frontend stay in sync automatically. Fallback hardcoded list in JS only kicks in if the API fetch fails (defensive).

## 2. Circulation factor — research findings

Consistent across 6 Indian civil-engineering sources (IS 3861-2002 and derivatives):

- Walls (external + internal) = 5-10% of plinth area for ordinary buildings, or 10-15% of plinth area when wall thickness is generous
- Horizontal circulation (passages, corridors) is 10-15% of plinth area; vertical circulation (staircase, lift) is 4-5% of plinth area
- Result: carpet area is typically 50-65% of plinth area for residential, with 65% as the target

**Translation to my factor**: plinth/carpet ratio = 1.54 to 2.00. But I'm not computing carpet/plinth — I'm computing `floor_area / sum(room_area)`, where "room" includes kitchen, bathroom, staircase. **My current 1.30 is at the optimistic end.** The middle of the realistic range is 1.35.

**Ephemeral-storage warning is surfaced to the user.** The Railway free-tier filesystem is ephemeral, so briefs get lost on redeploy. We disclose this in the save response payload and the frontend alert shows it. When Ramalingam upgrades to a paid tier with persistent volumes, the warning becomes stale but doesn't break anything. When migrating to Postgres (a likely v1.0 move), it's a swap of `sqlite3` calls for `psycopg` with no API/frontend changes.

**Token format validation prevents SQL injection.** `_is_valid_token_format` checks exact 24 hex chars before any DB query — so even if someone tries `"'; DROP TABLE briefs;--"` they never reach the SQL query.

### Architectural decisions worth noting

1. **One DB, one table, one index.** Over-engineering was tempting (per-user tables, migration system, audit log). I resisted. When we need those we'll add them, not before.

2. **SQLite via stdlib, not an ORM.** SQLAlchemy/Peewee would hide what's happening. Raw parameterized queries make every access explicit and safe.

3. **`existing_token` doesn't leak into stored payload.** I pop it off before serializing. Tested explicitly (`assert "existing_token" not in resumed["payload"]`).

4. **No email delivery.** Ramalingam's resume URL is copy-pasteable. Adding SMTP is real infra (deliverability, bounces, SPF/DKIM). When it's worth that cost, it's worth auth too — natural v1.0 pairing.

5. **Frontend gracefully degrades.** If the server save fails (network issue, service down), localStorage still works. User doesn't lose data because the backend had a bad day.
