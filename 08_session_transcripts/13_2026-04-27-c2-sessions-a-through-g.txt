You gave us your plot details, the home you want, and your budget. Component 2 ran 18 separate checks to answer one question:

Some checks need information you probably don't have:

#### #1 + #2: Scoring contract and `is_feasible` derivation

**The big one.** The reviewer is right that `overall_score: int` with no defined contract is dangerous — different engineers (or different sessions) will compute it differently, scores will drift between releases, and users will lose trust.

**Concrete contract:**
```python
def compute_overall_score(check_results: tuple[CheckResult, ...]) -> int:
    """Score is 100 minus weighted penalties.
    
    HARD_FAIL → cap score at 40 (dramatic visible drop)
    SOFT_WARN → -5 each (LOW confidence) or -10 each (MEDIUM/HIGH confidence)
    PASS → no penalty
    NOT_APPLICABLE → ignored
    
    Confidence-aware: a HIGH-confidence SOFT_WARN penalizes more than 
    a LOW-confidence one, because we trust the data more.
    """
```

And:
```python
@property
def is_feasible(self) -> bool:
    """Derived from blocking_issues — never set directly."""
    return len(self.blocking_issues) == 0
```

Plus expose `score_breakdown: dict[str, int]` so the user (and future-me) can audit which check contributed what.

**For the dual-design with `is_feasible_with_user_acceptance` we agreed on:**
```python
@property
def is_feasible(self) -> bool:
    """Strict feasibility — no user-accepted compromises counted."""
    return len(self.blocking_issues) == 0

@property  
def is_feasible_with_user_acceptance(self) -> bool:
    """User has accepted all listed compromises."""
    return len(self.unaccepted_blocking_issues) == 0
```
