### Drawback 1: Summary surfaces blocker count + names

The reviewer's concern was *"40 (1 blocker) vs 40 (3 blockers) — user can't differentiate severity."* Now both summary and full text show:

```
CODE-STRICT:   40/100 — NOT FEASIBLE (4 blockers)

```

The blocker count is inline with the score, and the first 3 blocker names are listed with a "+ N more" truncation. Both views distinguish "40 with one issue" from "40 with four issues" at a glance.

### Drawback 2: Downgraded warnings flagged in summary + lane details

The reviewer's concern: *"User may underreact to a HARD that was downgraded to SOFT because data is assumed."*

Two fixes:
1. **Lane details inline tag**: `! [STRUCTURAL] [DOWNGRADED FROM HARD] Soil type risk (Practical)`
2. **Summary note**: `Note: 1 warning(s) downgraded from HARD — verify data to confirm severity`

The full text OVERALL ASSESSMENT also shows the note. A user scanning the summary now knows immediately when a "warning" is actually a downgraded blocker.

### Drawback 6: Approval check SOFT_WARN at complex tier

The reviewer's concern: *"User underestimates approval friction for complex builds."*

Fix in `check_approval_complexity` — when `tier == "complex"` (16-40 weeks, multiple state/central NOCs, possibly EIA), severity is now `SOFT_WARN` instead of `PASS`. The message is rewritten to advise budget/timeline planning. Simple/medium tier still PASS.

This caused 1 of the 20 Session J scenarios (S12 Delhi G+3 1024+ sqm) to drop from 85 → 75 in Practical score. Still within its expected range, but real signal — exactly what the reviewer wanted.

### Drawback 9: JSON enriched with severity_label + category_label

The reviewer's concern: *"Frontend consumers must ship their own enum-to-label dictionary."*

Now every dict in the JSON output that has a `severity` field also has `severity_label`:
```json
{
  "severity": "hard_fail",
  "severity_label": "BLOCKING"
}
```

Same for `category` → `category_label`. Importantly, **gap severities and check severities map differently**:
- Check `hard_fail` → `BLOCKING`
- Gap `blocking_if_not_accepted` → `DECISION NEEDED`

The `_enrich_with_labels` function distinguishes them by the value itself (gap vocabulary vs check vocabulary). Raw `severity` field preserved for backward compatibility.

### Drawback 11: Inline category tags in lane details

The reviewer's concern: *"Legal violations ≠ comfort issues — user may treat them equally."*

Now every per-issue line in lane details has a category prefix:
```
  BLOCKING (3):
    ✗ [LEGAL] Setback compliance (Code-Strict)
    ✗ [STRUCTURAL] Soil type compliance (Code-Strict)
    ✗ [DESIGN] Solar exposure (Code-Strict)
```

User-facing labels chosen for clarity over technical accuracy:
- `compliance` → `LEGAL`
- `usability` → `DESIGN`
- `structural`/`cost`/`spatial`/`safety` → uppercase as-is

## The thing I need to be careful about

Indian construction is **bilingual on units**. I want to make sure I build what you actually want, not what I assume you want. Let me lay out what I see:

### What Indians actually use (in real life)

- **Plot size**: usually quoted in **square feet** ("30x40", "1200 sqft") OR **ground** (Tamil Nadu) / **cents** (Kerala) / **gunta** (Karnataka)
- **Plot dimensions**: usually feet ("30 feet by 40 feet" = 30x40)
- **Setbacks**: this is the awkward one. **NBC, DCRs, government documents are all in metres.** When an architect says "leave 1.5m setback", that's the official unit. But homeowners often think "5 feet setback".
- **Road width**: usually feet in conversation ("30 feet road") but DCR thresholds are in metres
- **Floor heights, room sizes**: feet in conversation ("12 feet ceiling", "10x12 bedroom")
- **Building plans**: drawings show both, but feet dominates conversation

### Where this matters in your engine

The entire backend (NBC rules, setback calculator, room minimums, KB files) is in **metres** because that's what the law uses. **I do NOT want to change that.** Changing the engine would mean rewriting the KB JSON files, the validation rules, the calculation logic, and risking breaking 913 tests.

What we should change is the **input/output layer** — the form the user fills in and the report they read.

### Three options, ordered by scope

**Option 1 — Quick: Form accepts feet, but stores/displays metres internally**

User types `30` and `40` into width/depth fields labeled "feet". JavaScript multiplies by 0.3048 before sending to the API. The API still gets metres, the engine never knows. Output report still shows metres.

- **Pro**: smallest change, lowest risk, ~30 minutes
- **Con**: report still in metres (so 1.5m setback, etc.)

**Option 2 — Better: Form accepts feet, OUTPUT also shows feet alongside metres**

Same as Option 1, plus: the report shows "1.5m (4.9 ft)" everywhere. User reads in their preferred unit, but official metres still visible.

- **Pro**: bilingual, honest about what authorities will check, user-friendly
- **Con**: a bit more work in the renderer (~1-2 hours)

**Option 3 — Toggle: User picks unit at top of form**

Radio button: "I'll enter in [ ] feet  [ ] metres". Form labels and the output report adapt to selection.

- **Pro**: serves both audiences perfectly
- **Con**: most work, more places to test (~3-4 hours), and honestly: most users will pick feet anyway

## My recommendation

**Option 2.** Reasons:

1. Indian users overwhelmingly think in feet for plot dimensions. Forcing metres input is a friction point.
2. But hiding metres entirely is dangerous — when your user goes to apply for permission, the BBMP / CMDA officer will check metres. Report needs to show what the official unit is.
3. Showing both (`1.5m (4.9 ft)`) is the honest answer. Users get their preferred unit, and they're prepared for what authorities will see.
4. Toggle (Option 3) is over-engineering for v1. Real user signal can tell us later if metres-only users exist.
