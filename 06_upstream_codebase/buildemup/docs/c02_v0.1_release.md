# Component 2 v0.1 — Release Summary

**Status:** Shippable. 871 PASS, 0 FAIL.

## What Component 2 does

Takes a captured Brief (from Component 1) plus optional verified data,
and produces a **DesignGapAnalysis**: two parallel feasibility reports
(Practical lens vs Code-Strict NBC compliance) with the gaps between
them, cost delta, and prioritized action steps.

## Architecture

### Inputs

- `Brief` from C1 (always required)
- `c7_cost_estimate` from C7 (optional — budget check returns N/A without it)
- `FeasibilityInput` wrapping 6 optional fields with provenance:
  - soil_type, water_table_depth_m
  - distance_from_electric_line_m, electric_line_type
  - distance_from_water_course_m, has_water_course_within_30m

### Output

`DesignGapAnalysis` containing:
- `practical_report: FeasibilityReport` (user's stated preferences applied)
- `code_strict_report: FeasibilityReport` (full NBC + DCR compliance)
- `gaps: tuple[Gap, ...]` (where the two lanes diverge — 0 to 6)
- `cost_delta_lakhs: float` (Code-Strict additions cost)
- `user_decisions_required: tuple[str, ...]` (questions for iteration UI)

Each `FeasibilityReport` has:
- `overall_score` (0-100, scoring contract: HARD caps at 40)
- `blocking_issues`, `soft_warnings`, `passed_checks`, `not_applicable_checks`
- `unknowns` (fields needing verification)
- `action_steps` (prioritized P1-P4)

## The 17 v0.1 checks

### Hard physics (4, unbranched)
1. envelope_sufficiency — plot - setbacks gives buildable area
2. floor_stack_feasibility — staircase + floor-area math works
3. parking_width — stilt parking minimum bay width
4. budget_feasibility — c7 cost vs user budget

### Legal-only (6, unbranched)
5. far_compliance — Floor Area Ratio vs city DCR
6. ground_coverage_compliance — % of plot built-on
7. fire_tender_access — road width + setbacks (NBC Part 4)
8. electric_line_clearance — distance from HT/LT lines (NBC)
9. water_course_clearance — 9m setback from drains/streams (NGT)
10. stilt_mandate_compliance — city DCR stilt requirements

### Branched (6, with Practical + Code-Strict + Gap)
11. setback_compliance — user setbacks vs city NBC mins
12. solar_exposure — orientation score (heuristic)
13. cross_ventilation — openable sides per plot type
14. soil_type — risk by soil + floor count
15. water_table — risk by depth + ground habitable
16. rwh — city mandate by plot tier

### Info-only (1)
17. approval_complexity — simple/medium/complex tier + timeline

### Deferred to v0.2
18. room_minimums — needs C1 to allow below-NBC room sizes (current
    `RoomRequirement.__post_init__` blocks them)

## Key design decisions (locked)

### Dual-design pattern
PRACTICAL = "what user wants" / CODE_STRICT = "what NBC strictly requires".
Both report 17 checks each (10 unbranched + 6 branched + 1 info).

### 3-state input pattern
USER_PROVIDED_VERIFIED / USER_PROVIDED_UNVERIFIED / USER_DOESNT_KNOW /
NOT_ASKED. InputField enforces source/value invariants in __post_init__.

### Downgrade rule (user-approved)
Assumed values that would HARD-fail → downgraded to SOFT_WARN.
User-provided values keep strict outcomes.

### Scoring contract
Start at 100, deduct -5/-7/-10 for SOFT_WARN by LOW/MEDIUM/HIGH confidence.
Any HARD_FAIL caps the score at 40 max.

### Cost delta computation
Soil verification ₹0.10L + WT verification ₹0.05L + RWH installation ₹1.0L
when not city-mandated. Total max v0.1 = ₹1.15L.

## API

`POST /api/feasibility/run` accepts JSON payload (C1 brief fields +
optional `feasibility_input` section + legacy electric/water-course kwargs)
and returns:

```json
{
  "ok": true,
  "trace_id": "...",
  "feasibility_summary_text": "...20-line CLI summary...",
  "feasibility_full_text": "...full report with sections...",
  "feasibility_data": { ...full DesignGapAnalysis JSON... },
  "brief_summary": { ... },
  "errors": null
}
```

Error handling:
- 400 for input validation failures (bad JSON, missing fields, invariant
  violations, unsupported city)
- 500 only for unexpected code bugs (with technical_detail)

## Deployment

The same `python -m buildemup.api.server` entry point that runs C1 now
also serves `/api/feasibility/run`. No additional dependencies required —
stdlib only. Works on Railway with the existing Procfile.

## What this means for the user (homeowner / architect)

Before C2: User entered a brief, got back C1's brief capture with
risk level + soft guidance.

Now: User entering the same brief gets back:
- Two scoring lanes telling them "what you want" vs "what code requires"
- Specific gaps where they've made trade-offs
- Estimated cost to upgrade to full code compliance
- List of unknowns + how to verify them (with cost + timeline)
- Prioritized action steps

This is the "feasibility report" deliverable — the foundation for everything
downstream (architectural design, cost optimization, contractor selection).

## Honest caveats

- **Scoring numbers are honest, not generous.** A score of 40 means
  "addressable issues exist" — most realistic briefs will land here on
  Code-Strict because verified soil/WT data is rare for homeowners.
- **City defaults are city-typical, not site-specific.** Verified data
  changes the outcome materially.
- **All gaps surface at first run.** Sessions H+ will add an interactive
  iteration UI where users accept/reject compromises.
- **This is feasibility, not architectural design.** A licensed architect
  is still required for build approval.
